# Process Factory

## Product

Process Factory is a modern process factory.

It is like a software factory, but instead of producing an application it produces a complete process in which humans and AIs work together.

## How it relates to the software factory

A software factory takes a request and produces working software. This repository is itself built by one: the Kaizen factory, which turns each request into a specification, tests, code and reviews.

Process Factory applies the same idea to a different result. What it produces is not an application but a process: a complete way of working in which humans and AIs each do their part.

## Status

The product is at its start. It cannot generate processes yet. What works today is one skill for Claude Code and the command line it drives: `/process <prompt>` creates a process under a short title that Claude writes from the prompt, stores the prompt with it and reports its id and its stage, `/process show` prints the board, `/process show <process-id>` prints one process, and `/process next <process-id>` runs the stage the process is in. Eight stages have a step. In `intake` a questioner agent reads the request and the organisation context and writes the questions a complete process needs to `questions-<n>.md` in the folder of the process, which then moves to `clarify`, or straight to `spec` when there is nothing to ask. In `clarify` Claude asks the user those questions one at a time and stores the answers, and the process moves to `spec`. In `spec` a spec writer agent writes `spec.md` in the folder of the process, with eleven sections that are each marked decided or open. When open sections need an answer from the user it writes the next `questions-<n>.md` and the process goes back to `clarify`, and when every section is decided Claude shows the specification and moves the process to `cases` after the user accepts it. In `cases` a case writer agent writes simulation cases from `spec.md` alone, never from a draft, one file `case-<n>.md` per case in the folder `cases` of the process, most of them for situations a reader of the specification would not think of, and the process moves to `draft`. In `draft` a draft writer agent writes the process document from `spec.md`, the organisation context and the cases to a new file `draft-<n>.md` in the folder `drafts` of the process, for the employee who has to follow it under pressure and with the name of a person at every role and every step, and the process moves to `review`. In `review` every reviewer that is installed reads the newest draft at the same time and writes one findings file in a new folder `round-<n>` in the folder `rounds` of the process, with a verdict of `PASS` or `CHANGES` and findings tagged `high`, `medium` or `low`, and the process moves to `rework` when a reviewer says `CHANGES` and to `approval` when all say `PASS`. In `rework` the draft writer reads the reviewed draft and every finding of the round and writes the next `draft-<n>.md` with only the changes the findings ask for, and the process moves back to `review`. The GDPR reviewer checks a draft for a lawful basis, data minimisation, the rights of the people the data is about, the notification of a breach to the authority and to those people in time, a processor agreement for every system the process uses, and what must be logged. The simulation reviewer plays the person in every case of the process with the draft and only what that person knows, and writes per case what they would do, where they would stop, what they would get wrong, and whether the case passes or fails and at which step. The readability reviewer checks that the employee who meets the draft for the first time in a real incident can follow it: one action per step, no term left undefined, no sentence that needs rereading, every decision point with a clear answer, and the first thing to do first. The legal reviewer checks the draft against the laws, agreements, policies, deadlines and duties that `spec.md` names and against who may decide what in `organisation/authority.md`, and ends every finding with the rule it comes from. Without a reviewer `next` on a process in `review` says so and moves nothing. In `approval` Claude asks who the owner of the process is when it has none, shows the newest draft, the verdict of every reviewer and the reason of a stop, and asks the user for their full name and whether they approve; the command line records the approval only when that name is the owner of the process, and the process stays in `approval`. For every other stage `next` reports the stage and moves nothing. `/process incident <process-id>` interviews the user about a real event the process was used in, what the process did not cover and what people actually did, and writes each thing it did not cover as a new file `case-<n>.md` in the folder `cases` of the process after the user confirms it, as a case every later version of the process must pass.

To use it in a project, add the package with `pnpm add -D github:Benjamsk/process-factory` and run `pnpm exec process-factory init` in the project's folder. That writes `.claude/skills/process/SKILL.md`, and `interviewer.md`, `questioner.md`, `spec-writer.md`, `case-writer.md`, `draft-writer.md` and `incident.md` next to it, together with `reviewer.md` and one file `<name>-reviewer.md` for every reviewer the package ships, and `/process` is available in the next Claude Code session there. Run `init` again after an upgrade.

The command line also keeps the process store. `process-factory new "<title>" "<prompt>"` creates a process: it makes `processes/<process-id>/` with `request.md`, which holds the title and under it the prompt, and the folders `cases`, `drafts`, `rounds`, `versions` and `feedback`, lists the process in `processes/board.json` in the stage `intake`, and prints its id. Only the `process-factory` command line writes the store, with six exceptions: the questioner writes `questions-<n>.md`, the spec writer writes `spec.md` and `questions-<n>.md`, the case writer writes the files `case-<n>.md` in `cases`, the draft writer writes `draft-<n>.md` in `drafts`, every reviewer writes its findings file in a folder `round-<n>` in `rounds`, and the interview of `/process incident` writes new files `case-<n>.md` in `cases`.

Every process is in one of the stages `intake`, `clarify`, `spec`, `cases`, `draft`, `review`, `rework`, `approval`, `published` and `regenerate`. `process-factory move <process-id> <stage>` moves a process to another stage and records the date and time of the change on the board; it refuses a move the state machine does not allow and names the stages that are allowed. `process-factory show` prints the board, and `process-factory show <process-id>` prints one process with its history. `process-factory answer <process-id> <file>` stores a file as `answers-<n>.md` next to the newest `questions-<n>.md` of a process in `clarify` and moves the process to `spec`. `process-factory accept-spec <process-id>` records on the board that the user accepted `spec.md` of a process in `spec` and moves the process to `cases`. It refuses while one of the eleven sections is not marked decided, names the open sections, and moves the process back to `clarify` when a `questions-<n>.md` has no answers yet. `move` never moves a process from `spec` to `cases`. The eleventh section, `Dependencies`, lists what the process rests on: laws and rules, roles, systems, agreements, policies and other processes. A move to `published` records on the board how the sections of `organisation/` describe the roles, systems, agreements and policies on that list. `process-factory check` lists every published process of which such a section has changed or is gone since then, and which one, as work waiting for the owner. `process-factory round <process-id>` records the newest round of a process in `review` on the board, with the draft it reviewed and the verdict of every reviewer, and moves the process to `rework` when a verdict is `CHANGES` and to `approval` when all are `PASS`. It refuses while the findings file of a reviewer is missing or malformed or its verdict does not fit its findings, and names the file. `process-factory show <process-id>` then prints the recorded rounds. A process gets at most five review rounds before a person decides: when the fifth recorded round of a process, or a later one, still has a verdict of `CHANGES`, `round` moves the process to `approval` instead of `rework`, records on the board that the loop stopped at the limit and which reviewers still ask for changes, and prints that reason, and `show <process-id>` prints it too. From `approval`, `move <process-id> rework` sends the draft back for one more round. In a rework the finding of a higher reviewer wins over a finding it contradicts, in the order legal, GDPR, simulation, readability, and the draft writer records every finding it dropped for that reason, with the finding that won and why, in `conflicts.md` in the folder of the round. When the simulation reviewer is installed, `round` also reads the result of every case from `simulation.md` and keeps it on the board with the round. It refuses a `simulation.md` that has no result for a case in the folder `cases` of the process, or whose verdict is `PASS` while a case fails, and names the cases. A case that passed in an earlier recorded round and fails in this one has regressed: `round` prints a line such as `Regressed: case 3 last passed in draft-2.md` for it and moves the process to `rework`, also at and past the limit of five rounds, so the loop ends only when no case regresses. Every process needs an owner before it can be approved: `process-factory owner <process-id> "<person>"` stores the name on the board, in every stage and again to change it, and refuses a name that does not stand in `organisation/roles.md` as whole words, letter for letter, outside the sections whose heading starts with `Example:`. `process-factory show <process-id>` prints the owner. `process-factory approve <process-id> --by "<person>"` approves the newest draft of a process in `approval`: it refuses a process without an owner, a name that is not the owner and an owner who is no longer named in `organisation/roles.md`, and writes who approved which draft and when to `approval-draft-<n>.md` in the folder `versions` of the process. The process stays in `approval`, and `move <process-id> published` is refused until the newest draft has such a file.

The factory reads what it knows about the organisation from the folder `organisation/`. `process-factory org init`, or `/process org init` in Claude Code, creates it with the files `roles.md`, `systems.md`, `processors.md`, `policies.md` and `authority.md`, each with one example section to replace. It writes only the files that are missing and never overwrites one. `/process org` in Claude Code interviews the user one area at a time, writes what it learns into these files, and lists in `organisation/unknown.md` what is still missing and which processes on the board it blocks.
