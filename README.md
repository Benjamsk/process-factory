# Process Factory

## Product

Process Factory is a modern process factory.

It is like a software factory, but instead of producing an application it produces a complete process in which humans and AIs work together.

## How it relates to the software factory

A software factory takes a request and produces working software. This repository is itself built by one: the Kaizen factory, which turns each request into a specification, tests, code and reviews.

Process Factory applies the same idea to a different result. What it produces is not an application but a process: a complete way of working in which humans and AIs each do their part.

## Status

The product is at its start. It cannot generate processes yet. What works today is one skill for Claude Code and the command line it drives: `/process <prompt>` creates a process under a short title that Claude writes from the prompt, stores the prompt with it and reports its id and its stage, `/process show` prints the board, `/process show <process-id>` prints one process, and `/process next <process-id>` runs the stage the process is in. Seven stages have a step. In `intake` a questioner agent reads the request and the organisation context and writes the questions a complete process needs to `questions-<n>.md` in the folder of the process, which then moves to `clarify`, or straight to `spec` when there is nothing to ask. In `clarify` Claude asks the user those questions one at a time and stores the answers, and the process moves to `spec`. In `spec` a spec writer agent writes `spec.md` in the folder of the process, with eleven sections that are each marked decided or open. When open sections need an answer from the user it writes the next `questions-<n>.md` and the process goes back to `clarify`, and when every section is decided Claude shows the specification and moves the process to `cases` after the user accepts it. In `cases` a case writer agent writes simulation cases from `spec.md` alone, never from a draft, one file `case-<n>.md` per case in the folder `cases` of the process, most of them for situations a reader of the specification would not think of, and the process moves to `draft`. In `draft` a draft writer agent writes the process document from `spec.md`, the organisation context and the cases to a new file `draft-<n>.md` in the folder `drafts` of the process, for the employee who has to follow it under pressure and with the name of a person at every role and every step, and the process moves to `review`. In `review` every reviewer that is installed reads the newest draft at the same time and writes one findings file in a new folder `round-<n>` in the folder `rounds` of the process, with a verdict of `PASS` or `CHANGES` and findings tagged `high`, `medium` or `low`, and the process moves to `rework` when a reviewer says `CHANGES` and to `approval` when all say `PASS`. In `rework` the draft writer reads the reviewed draft and every finding of the round and writes the next `draft-<n>.md` with only the changes the findings ask for, and the process moves back to `review`. The GDPR reviewer checks a draft for a lawful basis, data minimisation, the rights of the people the data is about, the notification of a breach to the authority and to those people in time, a processor agreement for every system the process uses, and what must be logged. Without a reviewer `next` on a process in `review` says so and moves nothing. For every other stage `next` reports the stage and moves nothing.

To use it in a project, add the package with `pnpm add -D github:Benjamsk/process-factory` and run `pnpm exec process-factory init` in the project's folder. That writes `.claude/skills/process/SKILL.md`, and `interviewer.md`, `questioner.md`, `spec-writer.md`, `case-writer.md` and `draft-writer.md` next to it, together with `reviewer.md` and one file `<name>-reviewer.md` for every reviewer the package ships, and `/process` is available in the next Claude Code session there. Run `init` again after an upgrade.

The command line also keeps the process store. `process-factory new "<title>" "<prompt>"` creates a process: it makes `processes/<process-id>/` with `request.md`, which holds the title and under it the prompt, and the folders `cases`, `drafts`, `rounds`, `versions` and `feedback`, lists the process in `processes/board.json` in the stage `intake`, and prints its id. Only the `process-factory` command line writes the store, with five exceptions: the questioner writes `questions-<n>.md`, the spec writer writes `spec.md` and `questions-<n>.md`, the case writer writes the files `case-<n>.md` in `cases`, the draft writer writes `draft-<n>.md` in `drafts`, and every reviewer writes its findings file in a folder `round-<n>` in `rounds`.

Every process is in one of the stages `intake`, `clarify`, `spec`, `cases`, `draft`, `review`, `rework`, `approval`, `published` and `regenerate`. `process-factory move <process-id> <stage>` moves a process to another stage and records the date and time of the change on the board; it refuses a move the state machine does not allow and names the stages that are allowed. `process-factory show` prints the board, and `process-factory show <process-id>` prints one process with its history. `process-factory answer <process-id> <file>` stores a file as `answers-<n>.md` next to the newest `questions-<n>.md` of a process in `clarify` and moves the process to `spec`. `process-factory accept-spec <process-id>` records on the board that the user accepted `spec.md` of a process in `spec` and moves the process to `cases`. It refuses while one of the eleven sections is not marked decided, names the open sections, and moves the process back to `clarify` when a `questions-<n>.md` has no answers yet. `move` never moves a process from `spec` to `cases`. The eleventh section, `Dependencies`, lists what the process rests on: laws and rules, roles, systems, agreements, policies and other processes. A move to `published` records on the board how the sections of `organisation/` describe the roles, systems, agreements and policies on that list. `process-factory check` lists every published process of which such a section has changed or is gone since then, and which one, as work waiting for the owner. `process-factory round <process-id>` records the newest round of a process in `review` on the board, with the draft it reviewed and the verdict of every reviewer, and moves the process to `rework` when a verdict is `CHANGES` and to `approval` when all are `PASS`. It refuses while the findings file of a reviewer is missing or malformed or its verdict does not fit its findings, and names the file. `process-factory show <process-id>` then prints the recorded rounds.

The factory reads what it knows about the organisation from the folder `organisation/`. `process-factory org init`, or `/process org init` in Claude Code, creates it with the files `roles.md`, `systems.md`, `processors.md`, `policies.md` and `authority.md`, each with one example section to replace. It writes only the files that are missing and never overwrites one. `/process org` in Claude Code interviews the user one area at a time, writes what it learns into these files, and lists in `organisation/unknown.md` what is still missing and which processes on the board it blocks.
