# The Kaizen software factory

Whichever Claude Code session runs this skill becomes the **orchestrator**. It runs the loop below, spawns every agent, and is the only writer of `factory/board.json`. The orchestrator always writes the board through `pnpm factory` (see `packages/factory/src/factory.ts`), never by hand. Every board change is mirrored to the dashboard at `/`. That database is the board's source of truth: `pnpm factory pull [job-id]` replaces `factory/board.json` (one job, or every job) and the job folders' mirrored Markdown files with what it holds, after a backup of `board.json`; every other command keeps reading the local file, so a pull is explicit and nothing gets slower.

Input: `$ARGUMENTS`

## Files hold the state

```
factory/                      in the main checkout only
  board.json                  durable state of every job, written only through pnpm factory
  board.lock                  held while a pnpm factory process writes board.json or backlog.md
  merge.lock                  held by the one job that is merging into main, through pnpm factory merge-lock
  test-run.lock               held by the one local vitest run or production build the CLI has started, through packages/factory/src/vitest-run.ts and packages/factory/src/production-build.ts, which both take it with withTestRunLock in packages/factory/src/merge-lock.ts
  backlog.md                  queue of features, one "- [ ] Title: details" line each, each optionally tagged "[serial: <group>]"
  findings.md                 things noticed while working, one "- [ ] <date> [<kind>] (<job-id>) <text>" line each, written by pnpm factory finding and by every move into blocked; no command starts work from it
  jobs/<job-id>/
    request.md                the feature as asked
    questions-<n>.md          clarifying questions from spec-writer (at most 2 rounds)
    answers-<n>.md            human answers to questions-<n>.md, written by pnpm factory answer or next
    spec.md                   written by spec-writer, may be edited by the human who accepts it
    acceptance.md             written by spec-writer: which locked test proves which criterion
    acceptance.json           the lock: blob shas of acceptance/<job-id>/, of the earlier acceptance tests spec.md names under Updated acceptance tests, and the red run, written by pnpm factory acceptance lock
    build.md                  written by builder
    tests-check.json          the whole-suite result of the last pnpm factory tests <job-id> check on a clean worktree, with the commit it tested and the failed tests; a later check of the same commit reuses it
    test-run.lock             held by the one pnpm factory tests <job-id> check that runs the suite for this job; a second check of the job waits for it and reuses its result
    round-<n>/                one folder per review round, one file per reviewer that ran (skipped reviewers write none)
      review-security.md      written by security-reviewer or security-reviewer-critical, whichever the round chose
      review-ux.md
      review-ui.md
      review-code.md
      review-scope.md
      review-acceptance.md
      review-regression.md
      review-accessibility.md
      review-schema-guard.md
      review-performance.md
    decision.md               written by approver
    rework-<n>.md             human feedback from /factory rework
    rebase-<n>.md             conflicts from rebasing a job on main, written by pnpm factory rebase
    refresh-<n>.md            reason and diff of a refresh of the locked acceptance tests, written by pnpm factory acceptance refresh and relock
    refresh.json              a started refresh, removed by relock or respec
    runs/<timestamp>.log      output of the headless Claude Code runs started by pnpm factory watch (not mirrored)
.claude/worktrees/<job-id>/   the job's git worktree on factory/<job-id>, created by pnpm factory worktree
.claude/worktrees/<job-id>-refresh/
                              the refresh worktree on factory/<job-id>-refresh-<n>, created from main by pnpm factory acceptance refresh
acceptance/<job-id>/          the job's locked acceptance tests, on its branch and merged into main with it
```

## Rules

- The main checkout stays on `main` and is used only for merges. Never check out a feature branch there. Before starting any job, run `git branch --show-current` in the main checkout. If it is not `main`, tell the user and stop.
- Every job's code lives in its own worktree at `.claude/worktrees/<job-id>`, on the branch `factory/<job-id>`. Agents read and change code only in that worktree.
- Every agent deletes files and folders in a worktree only with `pnpm factory rm <job-id> <path...>` (paths relative to the worktree), then stages the removal with `pnpm factory git <job-id> add <path>`, never with `rm`, `rmdir`, `del` or `git rm`. A missing module in a worktree is fixed with `pnpm factory worktree <job-id>`, never with `pnpm install`; when `node_modules` is there but unusable, `pnpm factory rm <job-id> node_modules` comes first.
- Agents read and write `factory/` only through absolute paths in the main checkout, never through a worktree's own `factory/` folder. `pnpm factory` always uses the main checkout's `factory/`, from wherever it runs.
- Agents get their context from files, not from the conversation, and each one writes only its own file, plus one line in `factory/findings.md` through `pnpm factory finding` (see Findings). Give every agent the job id, the worktree path and the exact absolute paths it reads and writes.
- A human accepts every spec before it is built. Never move a job to build without that acceptance (`pnpm factory stage` refuses it), and never edit `spec.md` after it has been accepted.
- Each review starts with `VERDICT: PASS` or `VERDICT: CHANGES`. `decision.md` starts with `APPROVE` or `ESCALATE`.
- The builder works and commits on the feature branch `factory/<job-id>` inside the job's worktree and tests against the spec's acceptance criteria.
- WAIT FOR ALL: a review round is done only when every selected reviewer's file exists in the round folder (pnpm factory verdicts reports complete: true). Never resume the builder mid-round.
- Spawn the builder with a name (`builder-<job-id>`) and resume that same builder with SendMessage for each new round, pointing it at the round folder. If it can no longer be resumed (a new session), spawn a fresh `builder-<job-id>` and point it at the worktree, `spec.md`, `acceptance.md`, `build.md` and the round folder.
- At most 2 fix rounds: if reviewers still ask for CHANGES after the builder has been resumed twice, run `pnpm factory stage <job-id> blocked "Reviews still request changes after 2 fix rounds"` and stop. The count starts again each time the job comes back to the builder from a rework or from a rebase with conflicts: a conflict with `main` is not a review finding.
- The factory pushes `factory/<job-id>` branches through `pnpm factory pr` and `main` only through `pnpm factory push-main` after a merge whose tests passed. It never pushes with `--force`; a rebased `factory/<job-id>` branch is pushed only with `--force-with-lease`, through `pnpm factory rebase` or `pnpm factory pr`. With `FACTORY_TEST_RUNNER=github`, the remote test runner in `packages/factory/src/vitest-run.ts` also pushes the worktree's HEAD with `--force-with-lease` to `factory/<job-id>`, and to `factory/<job-id>-refresh` and `factory/<job-id>-check` from the refresh and merge-check worktrees, the production build of `decide` in `packages/factory/src/production-build.ts` pushes the worktree's HEAD the same way to `factory/<job-id>` before it dispatches `.github/workflows/build.yml`, and `pnpm factory test-main` pushes the main checkout's HEAD the same way to `factory/merge-check-<job-id>` and deletes that branch after the run, so GitHub Actions can check the commit out; that is how `origin` first gets a job branch, before any pull request exists, and it is not a rule violation.
- Merge only jobs in the merge queue, one at a time, through **Merge queue**.
- Never edit, re-lock or delete a locked job's acceptance tests in `acceptance/<job-id>/` or its `acceptance.json`. If they are wrong, the job goes to a human. The lock also holds the earlier acceptance tests a later spec names under `Updated acceptance tests`; only that job's spec writer changes them, in the tests phase. One exception: `pnpm factory acceptance <job-id> reset` may discard them only after an edited spec acceptance, before the builder has started. A second exception: `pnpm factory acceptance <job-id> relock` rewrites the lock after a refresh (see **Refresh**), when the locked tests fail for a reason other than the job's code.
- If a step fails in a way you cannot recover from, run `pnpm factory stage <job-id> blocked "<what failed>"` and stop.
- Never resume, rework, rebase or merge an `archived` job. `pnpm factory stage`, `rework`, `rebase` and `check` refuse or skip it. If the user wants to continue it, they restore it first (see **Archived jobs**).
- **Record tokens**: each time an agent you spawned or resumed for a job finishes (spec-writer, acceptance-tester, builder-<job-id>, each reviewer (the security review under the agent that ran it, `security-reviewer` or `security-reviewer-critical`), approver), run `pnpm factory usage <job-id> <agent> <total_tokens> --duration-ms <duration_ms>` with the total tokens Claude Code reported for that run. Pass `--duration-ms` with the `duration_ms` Claude Code reported for that run; leave it out if none was reported. Pass the run's four token counts as well, `--input <n> --output <n> --cache-write <n> --cache-read <n>`, from the `input_tokens`, `output_tokens`, `cache_creation_input_tokens` and `cache_read_input_tokens` Claude Code reported for that run: the four go together and must add up to `<total_tokens>`, and a run recorded without them is priced at one blended rate instead of per token type. Add `--round <n>` for reviewers and for builder runs that fix round `<n>`. Add `--phase spec`, `--phase tests` or `--phase refresh` to every spec-writer run, naming the phase it ran: the spec phase (spec.md or questions), the tests phase or a refresh; a resume after a failed `lock` or `relock` belongs to the same phase. If no token count was reported, skip it. `pnpm factory usage` also records the agent's model, read from `.claude/agents/<agent>.md`, so nothing extra is passed. Never record your own tokens: `pnpm factory watch` records each headless run's own usage from the run's JSON result line as the agent `orchestrator` on the job the run was started for, and interactive sessions are not recorded. A failed `usage` call never blocks the job: tell the user and continue.

## Parallel runs

Several jobs can run at the same time. Each job has its own agents (`spec-writer-<job-id>`, `builder-<job-id>`, the ten reviewers including `acceptance-tester`, `regression-reviewer`, `accessibility-reviewer`, `scope-reviewer`, `schema-guard` and `performance-reviewer`, and `approver`) and its own worktree, and no job waits for another except in the merge queue, for the one local vitest run or production build at a time, and for a serial group: an item in `backlog.md` may carry a `[serial: <group>]` tag right after `- [ ]`, and the items of one group start one at a time in backlog order, each only once the previous one's job is merged, so it builds on that code. `pnpm factory` locks `factory/board.lock` around every board and backlog write, so concurrent calls do not lose updates. `pnpm factory watch` runs at most 7 jobs at once by default and accepts `--max-runs` up to 15; `pnpm factory next` accepts up to 15.

**Jobs that change the same files build one after another.** At every spec acceptance the factory compares the repository paths the accepted spec names (and the files in its acceptance lock) with those of every job in `build`, `review`, `merge-queue`, `needs-human` or `blocked` after its acceptance. A folder one job names covers the paths under it, except the paths in the other job's own `acceptance/<job-id>/` folder, where every job writes its own tests. On an overlap the accepted job is held in `build` with `waitsFor` and gets no builder run; the job history records the hold as `Held for <job> (<stage>): <files>`. Every pass of `pnpm factory watch` and every `pnpm factory next` looks at the holds again and drops each one whose job is merged or archived, is back in a stage before its spec acceptance, or is gone from the board, one hold at a time: `Hold dropped: <job> <stage>; still waits for <job>`. Once no hold is left the job is released with `Released: <job> <stage>` and `/factory resume <job-id>` starts. The dashboard card says which jobs it waits for and on which files; a human who knows the hold is wrong lets the job through with "Build anyway" on the dashboard or `/factory release <job-id>`.

**Merges run one at a time**, in merge queue order (see **Merge queue**). `pnpm factory merge-lock <job-id>` enforces this across every Claude Code session and headless run: it waits while another job holds `factory/merge.lock`. After every successful merge to `main`, run `pnpm factory check`: it records for every needs-human job whether its branch is still up to date with `main` and merges cleanly, and for every job in `review` whether a test merge of its branch with `main` is clean, has conflicts or fails locked acceptance tests of other jobs; a job in `build` is not test-merged, because the builder changes its branch anyway and the result goes stale, and `test-main` catches the same breakage after its merge. The test merge runs every job's acceptance tests in a temporary worktree, without touching the job's branch or worktree. The dashboard shows the result on the job. A needs-human job whose check says `conflicts` is not left for a human to approve: `pnpm factory watch` rebases it and sends the conflicts to the builder (see `/factory watch`); a check that comes back `clean` leaves the job where it is. A job whose check says `tests-fail` is not resumed, reworked or rebuilt by the factory; tell the user the failing tests, the jobs that locked them, and that the fix is `/factory respec <job-id> "<note>"` with a spec that names those tests under `Updated acceptance tests`. `pnpm factory check <job-id>` checks one job; `pnpm factory next`, `decide` (for a needs-human outcome) and `pnpm factory stage` to needs-human also run the check.

## Commands

## Job references

In every command below, `<job-id>` may be the full job id (`016-ids-in-dashboard-incremental-numbers`) or the job number: `#16`, `16` or `016`. The dashboard shows the number as `#16` on each job.

- Turn a number into the full id once, with `pnpm factory show <n>` (pass the plain number, such as `16`, or quote it as `"#16"`; never pass a bare `#16` in a shell, where `#` starts a comment). Its `id` field is the full id.
- Use the full id for every path, branch, worktree, agent name and merge command. Every `pnpm factory` command that takes a job also accepts the number, but its output always uses the full id.
- When telling the user about a job, give `#<n>` next to the id, for example: "`#16` (016-ids-in-dashboard-incremental-numbers) needs a human: run `/factory approve #16` to add it to the merge queue".

| Command | What it does |
| --- | --- |
| `/factory <feature>` | run a new job through the loop |
| `/factory next` | handle decisions made on the dashboard, then run the first unchecked item in `backlog.md` (same as `/factory next 1`) |
| `/factory next <n>` | handle decisions made on the dashboard, then run `pnpm factory next --count <n>` and run the loop for every returned job at the same time |
| `/factory accept <job-id>` | accept a spec-review job's spec from the terminal and run the loop from step 2 |
| `/factory release <job-id>` | let a held job build now |
| `/factory approve <job-id>` | add a needs-human job to the merge queue, or merge a job in the merge queue at its turn (never a blocked job) |
| `/factory rework <job-id> <note>` | send a job back to the builder with feedback |
| `/factory respec <job-id> <note>` | send a job in spec review, blocked, needs-human or the merge queue back to the spec writer for a fresh spec from main |
| `/factory answer <job-id> <answers>` | answer the spec writer's questions for a job in `clarify` and continue its spec |
| `/factory rebase <job-id>` | rebase one job in build or waiting for a human on main by hand |
| `/factory resume <job-id>` | continue a job from its current stage (`spec`, `build` or `review`); headless runs started by the watcher use it |
| `/factory watch` | explain how to start `pnpm factory watch`, which applies dashboard decisions on its own |
| `/factory login` | sign this terminal in to the dashboard with a code the human approves in the browser |

`pnpm factory tests <job-id> check [--base <ref>]` checks that a job's branch removed or disabled no tests compared with `main` and that the whole test suite passes in its worktree. The tests under `acceptance/` count the same way, the job's own and every earlier job's, and a changed file under another job's `acceptance/` folder that the job's `acceptance.json` does not list is a problem on its own (`Changes acceptance tests of other jobs: ...`). It counts test cases with a TypeScript syntax tree, so text in strings and comments does not count. It is read-only and prints `ok`, `green`, `problems` and `run`. It runs the whole suite once per commit: the result of a run on a clean worktree is recorded in `factory/jobs/<job-id>/tests-check.json` with the commit it tested and the failed tests, a later `tests check` of the same commit prints `Tests already ran on commit <sha>: reusing the result recorded at <checkedAt>` and reuses it instead of running the suite again, and a `tests check` that starts while another one runs the suite for the job waits for it (`factory/jobs/<job-id>/test-run.lock`) and then reuses its result. A red result is reused like a green one: a job that needs a fresh run gets a new commit, or a human deletes the file. The failed tests are printed on stderr as `Failed tests:` followed by one `  <file> > <name>` line each, so nobody reruns the suite to name them. `pnpm factory tests <job-id> report [--base <ref>]` lists, per changed test file, the tests the branch removed, added and changed, with their assertions before and after; it is read-only too.

`pnpm test` runs only the `unit` vitest project (every test outside `acceptance/`). `pnpm test:acceptance` runs the `acceptance` project (every job's acceptance tests). Builders run only their own job's acceptance tests, through `pnpm factory acceptance <job-id> check`; `pnpm factory acceptance <job-id> refresh <reason>` and `relock` refresh locked tests that fail for a reason other than the job's code (see **Refresh**); all acceptance tests run once in `pnpm factory decide`, where a failure blocks the merge, and again in Merging step 4.

### /factory <feature>

Pick a short title and a short slug of 2 to 5 meaningful words (lowercase, joined by hyphens, at most 40 characters, for example `stay-logged-in-longer`). Run `pnpm factory new "<title>" --details "<the feature as asked>" --slug <slug>`; the job id becomes `<NNN>-<slug>`. Run **the loop** for the returned job.

### /factory next [n]

Run `pnpm factory next --count <n>` (`n` defaults to 1, at most 15, 7 is a sensible maximum). It returns:

- `humanDecisions`: rework decisions made on the dashboard. Handle each one first, exactly like `/factory rework` (the note is in `details`).
- `queued` and `dequeued`: ids of jobs a human added to or removed from the merge queue on the dashboard. They are already applied; only report them to the user.
- `acceptedSpecs`: specs a human accepted on the dashboard, each with `jobId`, `acceptedBy`, `edited` (true when the human changed `spec.md`; the new text is already written) and `waitsFor`. These jobs are already in `build`. Run the loop from step 2 only for the entries whose `waitsFor` is empty, at the same time as the started jobs; for each held entry tell the user which jobs it waits for and on which files, and that `/factory release <job-id>` or "Build anyway" on the dashboard lets it through.
- `released`: ids of held jobs whose last hold was dropped, because the jobs they waited for are merged or archived or back before their spec acceptance. Their holds are already cleared. Run the loop from step 2 for each of them.
- `answered`: jobs whose questions were answered on the dashboard, each with `job` and `answersFile`. The answers are already written and each job is back in `spec`. Run **the loop** from step 1 for each of them, at the same time as the new jobs.
- `respecced`: jobs sent to respec on the dashboard, each with `jobId`, `file` (the `respec-<n>.md`) and `keptBranch`. They are already applied (worktree removed, earlier work kept on `keptBranch`, job back in `spec`). Run **the loop** from step 1 for each of them, at the same time as the new jobs.
- `archived` and `restored`: ids of jobs archived or restored on the dashboard. They are already applied (worktree removed, pull request closed or reopened); only report them to the user. Never resume an archived job. A restored job is back in the stage it had and waits for a human there, as before.
- `jobs`: the backlog items it started, in backlog order, each with `job`, `folder` and `requestFile`. Empty when the backlog is empty. Run **the loop** for every job **at the same time**. New jobs stop at spec review after step 1. It skips an item whose serial group waits for a job and starts the next startable item instead.
- `waiting`: the unchecked backlog items a serial group holds back, each with `title`, `group` and `waitsFor` (the job its group waits for). Nothing was started for them: tell the user which item waits for which job, and that it starts on its own once that job is merged.
- `job`: the first started job, or `null`.
- `warning`: say it to the user if present. It joins every warning with `; `, for example a spec acceptance that could not be applied.

Then run **Merge queue**, and repeat it for the next head, one job at a time, until `pnpm factory queue-next` returns no job.

### /factory accept <job-id>

Only for a job in stage `spec-review`. Run `pnpm factory accept <job-id>`. It records `Spec accepted by terminal` and moves the job to `build`, and prints the job. When its `waitsFor` is not empty, the job is held in `build` for the jobs it names, on the files it lists: tell the user which jobs it waits for and on which files, say that `/factory release <job-id>` or "Build anyway" on the dashboard lets it through, and do not run the loop. Otherwise run the loop from step 2.

### /factory release <job-id>

Only for a held job in `build` (`waitsFor` is not empty in `pnpm factory show <job-id>`). Run `pnpm factory release <job-id>`. It clears the hold with `Released by terminal` and prints the job; a job that is not held fails with `<job-id> is not held`. Then run the loop from step 2.

### /factory approve <job-id>

Check the stage with `pnpm factory show <job-id>`. Never approve a blocked job.

- `needs-human`: run `pnpm factory queue-add <job-id>`. It adds the job to the end of the merge queue and prints `{ jobId, stage, position }`. When it fails with `<job-id> cannot be added to the merge queue. The branch changed after the review: ...`, commits landed after the last review round. Tell the user the unreviewed commits the message names and that `/factory rework <job-id> <note>` gives the job a fresh review round; do not rework it on your own and do not move the branch.
- `merge-queue` and picked up (`pickedUp` is set, for example by a headless run the watcher started): run **Merge queue** from step 2, including the worktree removal and the `pnpm factory check` after `merged`.
- `merge-queue` and not picked up: run `pnpm factory queue-next` and merge the job through **Merge queue** from step 2 only if the command returns it. Otherwise tell the user its position in the queue (`pnpm factory queue`).

### /factory resume <job-id>

Read the stage with `pnpm factory show <job-id>`. For any stage, when `refresh.json` exists in the job folder, the refresh was started but not finished: continue at **Refresh** step 2. Otherwise:

- `spec`: if `spec.md` exists and `acceptance.json` does not, continue at the tests phase of step 1. If both exist, run the `spec-review` stage command of step 1 and stop. Otherwise run **the loop** from step 1.
- `build`: run **the loop** from step 2. First read `waitsFor`: when it is not empty the job is held for the jobs it names, so tell the user which jobs it waits for and on which files, say that `/factory release <job-id>` lets it through, and stop instead. If the job has a `rework-<n>.md` or `rebase-<n>.md` newer than its last review round (`round-<n>/`), point the builder at the newest one, as `/factory rework` and **Merge queue** do. Step 2.2 decides whether the acceptance tests are reset or written; if the job already has `acceptance.json` and its spec was not edited, the tests stay locked.
- `review`: run `pnpm factory worktree <job-id>` for the worktree `path`, then `pnpm factory verdicts <job-id>`. It prints the round number and every reviewer's verdict. Spawn only the reviewers whose verdict is `pending`, never a `skipped` one; for a pending security verdict spawn the agent recorded as `securityReviewer.agent` on the current round in `pnpm factory show <job-id>`, with its reason, exactly as in loop step 3, each with the job id, the round number, that `path` and its own file in `round-<n>/`, then continue at loop step 4. If it already reports `complete: true`, spawn no reviewer and continue at loop step 4.
- `archived`: tell the user the job is archived and must be restored first with `pnpm factory restore <job-id>`, and stop.
- Any other stage: tell the user there is nothing to resume, and stop.

### /factory watch

Tell the user to start `pnpm factory watch [--interval <seconds>] [--max-runs <n>]` in a terminal in the main checkout and keep it running; do not start it yourself. Every 30 seconds by default it sends a heartbeat to the dashboard, claims the decisions made there, applies spec acceptances, answers and rework notes with the same code as `pnpm factory next`, and starts one headless Claude Code run per job (`claude -p`, at most 7 at once by default and up to 15 with `--max-runs`; a run that was handed over to a terminal window no longer takes one of those slots, and its job starts no second run and refuses dashboard decisions while that window is still the job's run, except for its merge: once the job is first in the merge queue and not picked up, the watcher starts its `/factory approve` run with the window still open, and that run replaces the window as the job's run, so closing the window later changes nothing on the job). Headless runs started by it use `/factory approve <job-id>` for approvals and `/factory resume <job-id>` for everything else. It needs a terminal signed in with `pnpm factory login`, and `FACTORY_CLAUDE_COMMAND` and `FACTORY_CLAUDE_ARGS` choose the command and its extra arguments. `FACTORY_TEST_RUNNER` chooses where the vitest runs the CLI starts (`acceptance lock`, `check` and `relock`, `tests check`, `decide` and the merge checks of `check`, and `test-main`) and the production build of `decide` run: `github` runs them on GitHub Actions and pushes the branch first (see Rules), `local` or unset runs them on this machine, and any other value is refused; set it in the shell that runs `pnpm factory watch`, and the headless runs inherit it. When GitHub cannot start a run at all, the CLI runs those tests on this machine instead and prints `Tests run on this machine instead of GitHub: <reason>` on stderr and in the job history; that line is not a failure: do not block, resume or respec a job for it. Each headless run gets a fixed `--allowedTools` list: resume runs may edit, write, commit, rebase and run `pnpm factory` (including `pnpm factory git <job-id> ...`), the tests (`pnpm test` and `pnpm test:acceptance`), lint, tsc and the read-only `find` and `ls`; only approve runs may also `git merge` and run `git reset --hard HEAD~1`; neither may run `git push` itself or check out. A PreToolUse hook denies `rm`, `rmdir`, `del` and `git rm` with a pointer to `pnpm factory rm <job-id> <path...>`, `pnpm install` and `pnpm add` with a pointer to `pnpm factory worktree <job-id>`, and `find` with `-delete` or `-exec` with the same pointer to `pnpm factory rm`. That last deny reads the command as text and is best effort only: a quoted or substituted form of an action option can slip past it, so no run may use `find` to delete or write anything - deletion goes through `pnpm factory rm <job-id> <path...>`, and `find` is for listing. No allow rule lets a headless run edit files under `.claude/` (for example `.claude/skills/factory/SKILL.md` or `.claude/agents/*.md`): Claude Code treats them as sensitive and asks before every edit, even with `Edit` and `Write` allowed, and a headless run cannot answer; the factory's own files there are copies of `packages/factory/templates/`, so a job that changes the factory skill or an agent file changes the template and runs `cd <worktree> && pnpm factory init`, which copies every template into the worktree's `.claude/` through a Bash command that Claude Code does not check, and the builder stages the copies with `pnpm factory git <job-id> add .claude/agents .claude/skills` and commits them with the template. The watcher starts runs for such a job as for any other. Approve runs merge only through `pnpm factory merge <job-id>`, which merges the commit the reviewers saw, never with `git merge` on the branch, and push `main` only through `pnpm factory push-main <job-id>`. `FACTORY_CLAUDE_ARGS` is appended after that list and can add more. On every pass the watcher also starts the merge of the merge queue head on its own: it picks the job up as `pnpm factory queue-next` does and starts `/factory approve <job-id>`, one merge at a time. Dashboard approve requests add a needs-human job to the merge queue and dequeue requests take a waiting job out; the watcher applies both itself and starts no run for them. Dashboard `push-main` requests are applied by the watcher itself, like archive and restore, without starting a run. A dashboard Watch (request kind `watch`) is not a decision: it moves nothing on the job, is never a pickup and is not listed as pending. While the job's headless run is active the watcher opens a terminal window titled `Factory <job-id>` running `pnpm factory watch-session <job-id>`, which prints the run's Claude Code session transcript as it is written (assistant text and each tool call with its first line); with no active run it opens `claude --resume <session-id>` in such a window instead, the same hand-over as for a stuck run, and the job refuses dashboard decisions while that window is open. Before it opens a window of either kind the watcher raises the window titled `Factory <job-id>` when there is one, also one it did not open itself, so a job never gets a second window; every watch writes on the job whether it opened a window, raised it or found it already open. The watcher sends the jobs that have a window open with every heartbeat, and the dashboard refuses a watch for such a job and shows `A terminal for this job is open on the watcher's machine` on the ticket instead of the Watch button. `pnpm factory next` skips watch requests with a warning. While a job's headless run is active, every pass also reads the newest records of the run's transcript (the assistant text and tool calls `pnpm factory watch-session` prints) and uploads the last 30 of them to the dashboard, where the job panel shows them as Live output; the run's end drops them, they never go into board.json or the job's history, and `pnpm factory next` uploads nothing. On every pass the watcher also sends a `needs-human` job whose merge check says `conflicts` to the builder on its own, because nobody can merge it before it is rebased: it runs the same rebase as `pnpm factory rebase <job-id>`, and with `conflicts` the job is already in `build` with a `rebase-<n>.md`, so the watcher starts `/factory resume <job-id>`, which points the builder at that note as the `build` bullet of `/factory resume` says. With `rebased`, `up-to-date` or `skipped` the job stays in `needs-human` and its merge check is recorded again. The watcher tries each recorded check once per job and `main` commit, never touches a job in `blocked` or `archived`, and pushes nothing beyond what `pnpm factory rebase` does. A human still decides the merge: the job comes back through a review round and `decide` and lands in `needs-human` again, up to date with `main`. When a run ends without finishing, the job history shows the end of Claude's reply. A `/factory approve` run that ends with the job still picked up moves the job to `blocked`. A `/factory resume` run that ends with the job still in the stage it started in moves the job to `blocked`, with that message as its reason. Dashboard respec requests are applied by the watcher itself, which then starts `/factory resume <job-id>`. The watcher starts no run for a job its spec acceptance held (it logs `Held <job-id> for <job ids>`); on every pass it drops each hold whose job is merged or archived, is back in a stage before its spec acceptance, or is gone from the board, however many run slots are free, and once a job has no hold left it releases it, one per free run slot, and starts `/factory resume <job-id>` for it; a "Build anyway" on the dashboard is a resume request, which clears the hold and starts that run at once. It also continues a started serial group by itself: once the group's previous job is merged it starts the next item of that group, one per free run slot, logs `Started the spec of <job-id> to continue serial group <group>` and starts `/factory resume <job-id>` for it. Before it starts a run the watcher reads the machine's free physical memory and unused commit limit against `memory` in `factory.config.json` (by default 4096 MB free and 8192 MB of unused commit limit); while either is below its minimum the run is held back, not failed: the job's history gets `Waiting for the machine: <what is missing>; <prompt> starts when it has room`, the run keeps its `--max-runs` slot and starts on a later pass, and a run already in flight is never killed. A local vitest run or production build the CLI starts waits the same way after it has `test-run.lock` and prints `Waiting for the machine: <what is missing>; checking every 15 seconds until it has room` on stderr. Neither line is a failure: do not block, resume or respec a job for it. At the start of every pass the watcher compares the commit of `main` it started on with main's head: once the commits between them changed a file under `packages/factory`, it warns with both commits in its terminal and in its heartbeat warnings, runs no doctor, claims nothing and starts no more runs, drops the runs it was holding back for the machine, lets the active runs finish and exits with `Stopped: main changed packages/factory since this watcher started; start pnpm factory watch again`; start `pnpm factory watch` again, since nothing restarts it. A merge that changes nothing under `packages/factory` keeps it running. Stop it with Ctrl+C: the first press waits for the active runs, the second exits at once; a run it was still holding back for the machine does not start and says so on its job.

The orchestrator itself runs on the model of the Claude Code session. To run it on Sonnet, start it with `claude --model sonnet` for interactive runs, and set `FACTORY_CLAUDE_ARGS="--model sonnet"` for the headless runs started by `pnpm factory watch`. Agents with a `model:` in their frontmatter keep that model. `pnpm factory watch` records that `--model` value as the model of each run's `orchestrator` usage entry; without it the entry has no model and no price.

### Archived jobs

A human archives a job they no longer want, on the dashboard ("Archive" in the job panel) or with `pnpm factory archive <job-id>`. Only jobs in `spec-review`, `clarify`, `merge-queue`, `needs-human` or `blocked` that the factory is not working on can be archived. Archiving moves the job to stage `archived`, remembers the stage it had in `archivedFrom`, removes its worktree (never with `--force`; uncommitted work keeps it in place and the history says so) and closes its pull request. The branch `factory/<job-id>` is always kept.

`pnpm factory restore <job-id>` (or "Restore" in the dashboard's Archived list) moves the job back to `archivedFrom` and reopens its pull request; a job restored to `needs-human` gets a new merge check. Both commands print `{ jobId, stage, warnings }`; tell the user about any warning. `pnpm factory next` and `pnpm factory watch` apply dashboard archive and restore requests themselves and never start a Claude Code run for them.

### Blocked jobs

`blocked` ("Blocked" on the dashboard) is for operational failures: the factory did not finish the job (a failed build, no spec, acceptance tests that could not be locked, reviews that never passed, red acceptance tests, a merge that broke the tests), and a human has to find out why. `needs-human` is only for finished jobs that need a human judgement: an approver ESCALATE, sensitive files, changes to other jobs' acceptance tests, or a merge guard check the factory could not run (`Merge guard: Could not run the acceptance tests: ...`, `Could not run the acceptance suite: ...`, `Could not run the production build: ...`, `The acceptance tests were not run`, `Run pnpm factory worktree <job-id> first`, `Uncommitted changes under acceptance/`): the reviews passed and the approver decided, so the human judges the job from that reason and the merge check instead of sending it back. A blocked job is never approved or merged; it waits for `/factory rework`, `/factory respec` or an archive. A human runs `pnpm factory block-unfinished` once to move the needs-human jobs without an approver decision to blocked; it prints `{ blocked: [<job ids>] }`. Every move into blocked also appends an entry to factory/findings.md (see Findings).

### Findings

`factory/findings.md` is a plain list of things noticed while working that are not work yet. `pnpm factory finding "<title>: <details>" [--job <job-id>] [--kind bug|stall|low]` appends one dated line to it, `pnpm factory finding list` prints the entries with their numbers and `pnpm factory finding promote <n>` moves entry `<n>` into `backlog.md` as a `- [ ] Title: details` item and marks it promoted. No command starts work from the file.

The orchestrator records what it notices there itself, the same way the agents do: a test suite that exits red with no failing test, a lock file that no longer matches main, a dashboard that answered "payment required" for forty minutes. Every move into `blocked` appends a `stall` entry on its own, so every job the factory failed to finish is on the list. Only a human runs `promote`: a finding becomes a job when a person decides so.

### /factory rebase <job-id>

Rebase one job on main by hand. For a job in `build`, run `pnpm factory rebase <job-id>`, handle the result as loop step 2.3 does and continue as `/factory resume` does for `build`. For a job in `merge-queue` or `needs-human`, run it and handle the result as in **Merge queue** step 3, without the merge lock and without merging. With `rebased`, after the unit tests pass, also run `pnpm factory acceptance <job-id> check` in the worktree; when `ok` is false (`main` changed a file in the job's lock, or the locked tests no longer match `main`), run **Refresh** with its problems as the reason. With `rebased`, passing tests and a green check, the job stays where it was.

### /factory rework <job-id> <note>

Only for a job in stage `merge-queue`, `needs-human` or `blocked`. A job blocked before its spec was accepted (from `spec`, `clarify` or `spec-review`) cannot be reworked; send it to respec instead. Run `pnpm factory rework <job-id> "<note>"`, then `pnpm factory worktree <job-id>` (it reuses the job's worktree), then `pnpm factory rebase <job-id>` and handle its result as loop step 2.3 does. Resume or spawn `builder-<job-id>` pointing it at the worktree path, the returned rework file and, with `conflicts`, the rebase file too, then continue the loop from step 3 (review). The acceptance tests stay locked; do not rewrite the acceptance tests or run `lock` again. After the next fully passed round, `pnpm factory pr <job-id>` pushes the new commits to the same pull request.

### /factory respec <job-id> <note>

Only for a job in stage `spec-review`, `blocked`, `needs-human` or `merge-queue` that the factory is not working on. Run `pnpm factory respec <job-id> "<note>"`. It removes the job's worktree (never with `--force`), renames `factory/<job-id>` to `factory/<job-id>-respec-<n>` to keep the earlier work, writes `respec-<n>.md` with the note and the previous spec, removes `spec.md`, `acceptance.md`, `acceptance.json`, `build.md` and `decision.md`, and moves the job to `spec`. It prints `{ jobId, stage, file, keptBranch }`. Then run **the loop** from step 1, passing `respecFiles` from `pnpm factory spec <job-id>` to the spec writer. The spec writer gets no new question rounds. On the dashboard, "Send back to spec" in the spec review panel queues the same respec with a note; `pnpm factory next` and `pnpm factory watch` apply it like every other dashboard respec request.

### /factory answer <job-id> <answers>

Only for a job in stage `clarify` (check with `pnpm factory show <job-id>`). Run `pnpm factory answer <job-id> "<answers>"`. It writes `answers-<n>.md` and moves the job back to `spec`. Then run **the loop** from step 1 for that job.

### /factory login

Run `pnpm factory login` as a background command: it prints two lines at once and then waits for the human. Read those first lines, give the human the URL and the code they hold, and tell them to open the URL in a browser where they are already signed in to the dashboard and to approve that code only because they asked for this login. Never ask for a password or a 2FA code in the conversation, and never print the token. Then wait for the command to end and report the username it printed, or its error (`The login code expired or was not approved; run pnpm factory login again` means the code was not approved within 10 minutes). `pnpm factory logout` signs this terminal out again, and the dashboard's `Terminals` page revokes the token of a machine the human no longer has.

## The loop (edit this to change the factory)

```
feature -> spec-writer (opus) -> [questions -> clarify <- answer] -> spec-writer -> worktree
        -> spec-writer tests phase -> acceptance lock (red) -> spec-review (human accepts spec + tests, may edit)
        -> [edited: acceptance reset -> spec-writer tests phase -> acceptance lock (red)]
        -> rebase on main -> builder (opus) -> security (opus) or security-critical (claude-fable-5-1) | ux (sonnet) | ui design (sonnet) | code (opus) | scope (sonnet) | acceptance-tester (opus) | regression (opus) | accessibility (sonnet) | schema guard (opus) | performance (opus)
        -> WAIT FOR ALL selected -> any CHANGES: rebase on main -> resume builder (max 2 rounds) -> all PASS: pull request -> approver (opus)
        -> APPROVE: merge queue | ESCALATE: needs-human -> /factory approve (queue-add) -> merge queue | /factory rework
        merge queue head (one at a time) -> rebase on main -> tests -> merge to main -> remove worktree
                                         -> [conflicts or red tests: builder -> review -> decide -> merge queue]
                                         -> [locked tests fail for another reason: refresh -> relock -> continue]
```

1. **Spec**: the job starts in stage `spec`. Run `pnpm factory spec <job-id>`. It returns the absolute `requestFile`, `specFile`, `questionsFile`, `answerFiles` and `respecFiles`, and `canAsk`. Run `pnpm factory log <job-id> "Spec writer: writing the spec or clarifying questions"`, then spawn `spec-writer` with the name `spec-writer-<job-id>`, the job id, all of those paths (including every `respecFiles` entry) and `canAsk`; it reads the code on `main` in the main checkout and writes either `spec.md` or `questionsFile`. Each time the spec writer finishes, record its tokens (`pnpm factory usage <job-id> spec-writer <total_tokens> --phase spec --duration-ms <duration_ms>`, see **Record tokens**). Afterwards:
   - If `spec.md` exists, the spec writer also writes the failing acceptance tests before the spec goes to review (the **tests phase**):
     1. Run `pnpm factory worktree <job-id>`. It creates `factory/<job-id>` from `main` if needed, creates or reuses `.claude/worktrees/<job-id>`, installs its dependencies, and returns the absolute `path`.
     2. Run `pnpm factory log <job-id> "Spec writer: writing the failing acceptance tests"`, then resume `spec-writer-<job-id>` with SendMessage for the tests phase, giving it that `path` and the absolute paths of `spec.md` and `acceptance.md` in the main checkout. If it cannot be resumed, spawn a fresh `spec-writer-<job-id>` for the tests phase with the same paths. It writes failing tests in `acceptance/<job-id>/`, commits them and writes `acceptance.md`. When it finishes, record its tokens with `pnpm factory usage <job-id> spec-writer <total_tokens> --phase tests --duration-ms <duration_ms>`.
     3. Run `pnpm factory acceptance <job-id> lock`. It checks that the branch holds only the new tests and that they fail, then writes `acceptance.json`. It also locks the earlier acceptance tests `spec.md` names under `Updated acceptance tests`, which only the spec writer changes, in the tests phase. If `lock` fails, resume the spec writer once with the error message, then run `lock` again. If it fails a second time, run `pnpm factory stage <job-id> blocked "Acceptance tests could not be locked: <error>"` and stop.
     4. If the spec writer replies `NO WORK NEEDED: <reason>`, do not run `lock`. Run `pnpm factory stage <job-id> spec-review "Spec recommends closing the job: <reason>"` and stop this job. Tell the user the spec recommends closing it: a human archives it on the dashboard (or with `pnpm factory archive <job-id>`), or edits the spec into one that builds and accepts it.
     5. If the spec writer replies `NO EXECUTABLE TESTS: <reason>`, run `pnpm factory stage <job-id> blocked "No executable acceptance tests"` and stop.
     6. After a successful lock, run `pnpm factory stage <job-id> spec-review "Spec and failing acceptance tests written; waiting for a human to accept them"`. Stop this job here and tell the user it is waiting for spec review on the dashboard (`/`), or for `/factory accept <job-id>`.
   - Else, if `questionsFile` exists, run `pnpm factory ask <job-id>`. It moves the job to `clarify` ("Needs answers" on the dashboard). Show the questions to the user and stop **this job only**; other jobs keep running. The job continues after `/factory answer` or answers sent from the dashboard and picked up by `/factory next`. At most 2 question rounds: after that `canAsk` is `false` and the spec writer must write the spec.
   - Else run `pnpm factory stage <job-id> blocked "Spec writer wrote no spec"`.
   **Spec review**: the job continues only after a human accepts the spec, either with `pnpm factory accept <job-id>` (`/factory accept`) or on the dashboard, which `pnpm factory next` reports in `acceptedSpecs`. In both cases the job is already in `build`; go on with step 2 unless it is held (`waitsFor` is not empty), in which case it waits.
2. **Build**: the job is already in `build` after its spec was accepted, so do not move it there yourself.
   1. Run `pnpm factory worktree <job-id>`. It creates `factory/<job-id>` from `main` if needed, creates or reuses `.claude/worktrees/<job-id>`, installs its dependencies, and returns the absolute `path`.
   2. **Acceptance tests**: the tests were normally written and locked in step 1, before spec review.
      - If the accepted spec was edited (`acceptedSpecs[].edited` is true), run `pnpm factory acceptance <job-id> reset` first. It discards the tests and `acceptance.json` and `acceptance.md`, and refuses once a review round or `build.md` exists.
      - Then, if `acceptance.json` does not exist (after a reset, or for a job that reached build without tests), run the spec writer's tests phase and `lock` exactly as in step 1, with the same retry and blocked rules, but do not move the job to `spec-review`. If the spec writer replies `NO WORK NEEDED: <reason>` there, the human accepted a spec that still recommends closing the job: run `pnpm factory stage <job-id> blocked "Spec recommends closing the job: <reason>"` and stop.
      - Otherwise skip this step; the tests stay locked.
   3. **Rebase**: run `pnpm factory rebase <job-id>`. The branch was cut from `main` in step 1 and `main` may have moved since, so a conflict is found now, before any build or review work is spent on a stale base, instead of at the merge queue. With `up-to-date` or `rebased`, continue. With `conflicts`, the job stays in `build`, `rebase-<n>.md` is written and its absolute path is `file`: give the builder that file in step 2.4 too, so it resolves the conflicts first, as `/factory resume` and **Merge queue** do. With `skipped` (the command has logged the reason on the job), or when the command fails, tell the user and continue with the builder on the branch as it is: a job is never moved to `blocked` here, because no review work has been spent yet, and the **Merge queue** rebase remains the last check. Do not run `pnpm factory acceptance <job-id> check` here: the locked tests are red until the builder has run, and the acceptance tester runs the check in the next round. Never rebase a job in `review`, neither while its round is open (**Wait for all**) nor between `pnpm factory round` and `decide`: `decide` judges the `reviewedCommit`, and `pnpm factory rebase` refuses a job in `review`.
   4. Spawn the `builder` named `builder-<job-id>` with that `path`, the absolute paths of `spec.md`, `acceptance.md` and `build.md` in the main checkout, and the folder `acceptance/<job-id>/`. It makes the locked tests pass without changing them, works and commits in the worktree and writes `build.md`. When it finishes, record its tokens with `pnpm factory usage <job-id> builder <total_tokens> --duration-ms <duration_ms>`. Before resuming or spawning a builder for a later round or a rework, run steps 2.1 and 2.3 again; the worktree is reused and the branch is rebased on `main` first. Before you spawn or resume the builder in this step, run `pnpm factory log <job-id> "Builder: making the acceptance tests pass"`, so the job's history names the step while the builder works.
3. **Review**: run `pnpm factory round <job-id>`. It moves the job to `review`, creates `round-<n>/`, returns each reviewer's file path and marks the reviewers the diff does not need as skipped. It also prints `security: { agent, reason }`: which of `security-reviewer` (opus) and `security-reviewer-critical` (claude-fable-5-1) reviews this round for security, and why. The critical one runs when the diff touches a path in `criticalPaths` of `factory.config.json` or when the diff cannot be read, the standard one otherwise; both write `review-security.md` and the `security` verdict, so nothing after the round changes. Then run `pnpm factory reviewers <job-id>`. It prints `run`, the reviewers to spawn for the diff `main...factory/<job-id>`, and `skipped` with a reason per skipped reviewer: `ui-design-reviewer`, `ux-reviewer` and `accessibility-reviewer` run only when app pages, components or styles changed, `code-reviewer` and `scope-reviewer` only when a file other than Markdown changed, `schema-guard` only when a file under `schemaPaths` of `factory.config.json` that is not a test file changed, `performance-reviewer` only when a file under `performancePaths` of `factory.config.json` that is not a test file changed, and `security-reviewer`, `acceptance-tester` and `regression-reviewer` always; when the diff cannot be read, every reviewer runs (the schema guard only when `schemaPaths` is set, the performance reviewer only when `performancePaths` is set). Spawn only the reviewers in `run`, chosen from the security agent `pnpm factory round` printed as `security.agent`, which also gets `security.reason`, `performance-reviewer`, `schema-guard`, `ux-reviewer`, `ui-design-reviewer`, `code-reviewer`, `scope-reviewer`, `acceptance-tester`, `regression-reviewer` and `accessibility-reviewer` **in parallel**, and do not spawn or wait for a skipped reviewer. The selection is evaluated again at every round, so a fix round that adds UI files gets the UI reviews. Give each the job id, the round number, the worktree path and its own output file. The regression reviewer runs `pnpm factory tests <job-id> check` in the worktree, which fails when the branch deleted, removed or disabled tests, under `acceptance/` as well as elsewhere, changed another job's acceptance file outside its lock, or the whole suite does not pass. The reviewers of a round share one whole-suite run: `tests check` records its result per commit, so the builder's own check of the reviewed commit, the regression reviewer and anyone else who checks that commit see the same result and the round costs one suite run. It also runs `pnpm factory tests <job-id> report` and returns CHANGES when an existing test was rewritten or weakened to turn green instead of the code being fixed. The acceptance tester runs `pnpm factory acceptance <job-id> check` and maps every acceptance criterion to a test that runs and passes. The code reviewer runs only the type check and lint. The scope reviewer checks the diff against `spec.md` and the YAGNI and small-diff rules in `CLAUDE.md`. The schema guard checks that changed schemas and stored formats still work with existing data, or come with a tested migration or tested code that still reads the old shape. The performance reviewer checks the diff for N+1 and unbounded database queries, queries without a supporting index, client components that could be server components, and polling or re-rendering that is heavier than needed; it does not build the project. Each time one finishes, run `pnpm factory verdicts <job-id>` so its chip fills in on the dashboard, and record its tokens with `pnpm factory usage <job-id> <agent> <total_tokens> --round <n> --duration-ms <duration_ms>`, which records them under that agent name. If `unreadable` lists a file, ask that reviewer to fix its first line. Before you spawn the reviewers, run `pnpm factory log <job-id> "Reviewers: running <agents>"`, where `<agents>` is the agents you are about to spawn, separated by a comma and a space (for example `Reviewers: running security-reviewer, code-reviewer, acceptance-tester, regression-reviewer`).
4. **Wait for all**: continue only when `pnpm factory verdicts <job-id>` reports `complete: true`.
   - If `acceptance-tester` wrote a finding in `review-acceptance.md` that starts with `locked-tests:` (the locked tests cannot pass for any correct implementation, a spec problem), do not resume the builder. Run **Refresh** with the finding as the reason: the spec writer rewrites the locked tests on top of `main` and the job continues. Only when the spec writer replies `NEEDS RESPEC` (**Refresh** step 3), run `pnpm factory stage <job-id> blocked "Locked acceptance tests cannot pass: <finding>"`, then `pnpm factory respec <job-id> "<finding>"`, then run **the loop** from step 1 for this job, passing `respecFiles` from `pnpm factory spec <job-id>` to the spec writer, as `/factory respec` does. The `stage ... blocked` step is needed because `pnpm factory respec` accepts only jobs in `merge-queue`, `needs-human` or `blocked`. The respecced job ends in `spec-review` as usual, so a human still accepts the new spec and tests before the next build. If `pnpm factory respec` fails (for example the worktree has uncommitted changes), the job stays in `blocked`; report the error and stop.
   - If `changesRequestedBy` is not empty: run `pnpm factory stage <job-id> build "Round <n>: changes requested by <reviewers>"`, then steps 2.1 and 2.3 (the worktree and the rebase on `main`), then resume `builder-<job-id>` with SendMessage pointing it at `factory/jobs/<job-id>/round-<n>/` in the main checkout and, with `conflicts`, at the returned `rebase-<n>.md` too. When it finishes, record its tokens with `pnpm factory usage <job-id> builder <total_tokens> --round <n> --duration-ms <duration_ms>`, then go back to step 3. Before you resume the builder, run `pnpm factory log <job-id> "Builder: fixing the changes requested in round <n>"`.
   - If every reviewer passed: run `pnpm factory pr <job-id>`. It pushes `factory/<job-id>` to `origin` and opens a GitHub pull request against `main`, or reuses the open one, and records its link on the job. If it returns a `warning` (for example `gh` is missing or the push was rejected), tell the user the warning and continue; the job is not blocked. Then spawn the `approver` with the job id, the absolute path of `factory/jobs/<job-id>/` and the absolute path of `decision.md`, and nothing more: no summary of what the reviewers found, how the tests ran or what the diff touches, and no counts. It reads the job folder and runs the diff itself and writes `decision.md` with an `## Evidence` section. When it finishes, record its tokens with `pnpm factory usage <job-id> approver <total_tokens> --duration-ms <duration_ms>`.
5. **Decide**: run `pnpm factory decide <job-id>`. It first refuses a `decision.md` whose `## Evidence` section does not name `spec.md`, every review file of the latest round and the diffstat of `main...factory/<job-id>` (its error starts with the path of `decision.md` and ends with `missing: ...`), and records nothing then. Spawn a fresh `approver` once with the same paths and the error message, then run `decide` again. If it is refused a second time, run `pnpm factory stage <job-id> blocked "Approver decided without evidence: <error>"` and stop. It records the decision and runs a fixed merge guard that escalates sensitive or unreviewed changes, jobs whose acceptance tests were never locked or changed after the lock, and jobs whose locked acceptance tests are not green (it runs them, as `pnpm factory acceptance <job-id> check` does). The merge guard also runs every acceptance test in `acceptance/` in the job's worktree and blocks the job when they are not green. It also runs the production build (`pnpm build`) in the job's worktree, or on GitHub Actions (`.github/workflows/build.yml`) with `FACTORY_TEST_RUNNER=github`, when a file other than Markdown changed, and blocks the job with `Merge guard: Production build failed: <first error>` when it fails. It judges the commit the reviewers saw (recorded by `pnpm factory round`) and sends the job to a human when the branch changed after the review. It never merges. It also refuses, and records nothing, unless it is run in the main checkout, the main checkout is on `main`, and the factory code and `factory.config.json` there are identical to the commit `main`; its error then starts with `factory: Decide runs only in the main checkout`, `factory: Decide from main:`, `factory: The factory code that is running is in` or `factory: The merge guard differs from main:`. On such an error change, commit and discard nothing in the main checkout: run `decide` once more from the main checkout, and when it is refused again run `pnpm factory stage <job-id> blocked "Merge guard could not run: <error>"` and stop. Before it records a decision, `decide` also compares the board's verdicts of the latest round with the review files the reviewers wrote and recomputes which reviewers were allowed to be skipped; every mismatch, including a reviewer the board shows as `pending` while its review file names a verdict, blocks the job with a reason that starts with `Merge guard: <Reviewer> review: board.json says`.
   - `outcome: "ready-to-merge"`: do **not** merge here. The job is in the merge queue (stage `merge-queue`, shown as "Merge queue") with its worktree and branch, and the factory merges it on its own at its turn. A needs-human job that a human added to the queue earlier comes back as `ready-to-merge`. Tell the user: "`#<n>` (`<job-id>`) is in the merge queue."
   - `outcome: "blocked"`: the job is unfinished (for example a review that did not pass, red acceptance tests or a failed production build). Report its reasons to the user; it waits for `/factory rework`, `/factory respec` or an archive, and is never merged. Except: when a reason is `Merge guard: Acceptance suite is not green: ...` and no reason names the job's own locked tests (`Acceptance tests are not green`, `Acceptance tests changed after they were locked`), the job's build breaks another job's acceptance test: run `pnpm test:acceptance` in the worktree to name the failing earlier test files, then run **Refresh** with them and their failures as the reason.
   - `outcome: "needs-human"`: `decide` has already recorded a merge check (behind `main` or not, clean or conflicting) that the dashboard shows. The job keeps its worktree and waits for `/factory approve` (which adds it to the merge queue), `/factory rework` or a decision on the dashboard. A job whose reviews passed also lands here when a guard check could not run (a reason starting with `Merge guard: Could not run`, or `Merge guard: The acceptance tests were not run`): nothing is known to be wrong with the branch, so judge it from the reason and the merge check.

Finish by telling the user each job's `#<n>`, its id and its final stage. For jobs in `merge-queue`, say they are in the merge queue. For jobs in `needs-human` or `blocked`, give the reasons. For each job in `clarify`, list its questions and say how to answer them (`/factory answer <job-id> <answers>` or the dashboard).

## Merge queue

Jobs in stage `merge-queue` ("Merge queue" on the dashboard) wait in the merge queue, in the order they entered it. A job joins it when `decide` returns `ready-to-merge`, or when a human adds a needs-human job with `pnpm factory queue-add <job-id>`, `/factory approve <job-id>` or "Add to merge queue" on the dashboard. `queue-add` and the dashboard refuse a needs-human job whose branch head is not its `reviewedCommit`: the card then shows `Branch changed after the review` and a human sends the job back with `/factory rework <job-id> <note>` for a fresh review round. `pnpm factory queue-remove <job-id>` (or "Remove from merge queue" on the dashboard) takes a waiting job back to `needs-human` and prints `{ jobId, stage }`; the job that is merging cannot be removed. `pnpm factory queue` prints `{ queue: [{ position, jobId, title, merging }] }`. Only the head job is rebased, at its turn:

1. Run `pnpm factory queue-next`. It picks up the first job in the queue and prints `{ jobId }`, or `{ jobId: null, reason }` while another job is merging or when the queue is empty. If `jobId` is null, stop. A headless `/factory approve <job-id>` run started by the watcher finds its job already picked up and skips this step.
2. Run **Merging** step 1 (`pnpm factory merge-lock <job-id>`).
3. Run `pnpm factory log <job-id> "Merging: rebasing on main"`, then `pnpm factory rebase <job-id>`. With `up-to-date`, continue. With `rebased`, run `pnpm factory worktree <job-id>`, then `pnpm factory log <job-id> "Merging: testing the rebased branch"`, then `pnpm test -- --run` in the worktree; if `warning` is set (the push to its pull request failed), tell the user. After `pnpm test -- --run` passes, run `pnpm factory acceptance <job-id> check` in the worktree; when `ok` is false, run **Refresh** (the job keeps the merge lock through it; a job that comes out green continues to step 4). If those tests fail, run `pnpm factory rework <job-id> "Tests fail after rebasing on main: <short summary>"` and `pnpm factory merge-unlock <job-id>`, then continue as `/factory rework` does. With `conflicts`, the job is already in `build`: run `pnpm factory merge-unlock <job-id>` and point the builder at the returned `file` (loop step 2.4); after the builder resolved them and before the review round, run `pnpm factory acceptance <job-id> check` in the worktree and run **Refresh** when `ok` is false; otherwise the locked acceptance tests stay as they are. With `skipped`, or when the command fails, run `pnpm factory stage <job-id> blocked "Rebase on main failed: <reason>"` and `pnpm factory merge-unlock <job-id>`. Continue to step 4 only after `up-to-date`, or after `rebased` with passing tests and a green acceptance check. A job rebased before its build (loop step 2.3) is rebased here again when `main` moved since; this rebase stays as the last check before the merge.
4. Run **Merging** steps 2 to 8.

`/factory next` and `pnpm factory watch` repeat this for the next head, one job at a time. A job sent back to the builder rejoins the queue on its own after its next passed review and `decide`.

## Refresh

When a job's locked acceptance tests fail for a reason other than the job's code (`main` moved on, `main` changed a file in the lock, the build breaks an earlier job's acceptance test, or the acceptance tester found a locked test that cannot pass), refresh them instead of blocking. `spec.md` stays unchanged.

1. Run `pnpm factory acceptance <job-id> refresh "<reason>"`, where the reason names the failing tests and why (the `check` problems, the vitest failure summary, decide's reason or the `locked-tests:` finding). It prints `path`, `file`, `specFile` and `acceptanceFile`.
2. Run `pnpm factory log <job-id> "Spec writer: refreshing the locked acceptance tests"`, then resume `spec-writer-<job-id>` with SendMessage in refresh mode (or spawn a fresh `spec-writer-<job-id>`), giving it the job id, `path`, `specFile`, `acceptanceFile` and `file`. Record its tokens with `pnpm factory usage <job-id> spec-writer <total_tokens> --phase refresh --duration-ms <duration_ms>`.
3. If it replies `NEEDS RESPEC: <reason>`: if the job holds the merge lock, run `pnpm factory merge-unlock <job-id>` first. Then run `pnpm factory stage <job-id> blocked "Locked acceptance tests cannot pass: <finding>"`, then `pnpm factory respec <job-id> "<finding>"` (it removes the started refresh), then run **the loop** from step 1 for this job, passing `respecFiles` from `pnpm factory spec <job-id>` to the spec writer, as `/factory respec` does. The respecced job ends in `spec-review` as usual.
4. Otherwise run `pnpm factory worktree <job-id>` and `pnpm factory acceptance <job-id> relock`. If `relock` fails, resume the spec writer once with the error message, then run `relock` again. If it fails a second time, run `pnpm factory stage <job-id> blocked "Acceptance tests could not be refreshed: <error>"` (and `pnpm factory merge-unlock <job-id>` if the job holds the merge lock) and stop.
5. Run `pnpm factory acceptance <job-id> check` in the job's worktree: the refreshed tests against the job branch. If `ok` is false, the job goes back to the builder: for a job in `merge-queue`, `needs-human` or `blocked` run `pnpm factory rework <job-id> "Refreshed acceptance tests fail on the branch: <problems>"`, otherwise `pnpm factory stage <job-id> build "Refreshed acceptance tests fail on the branch: <problems>"`; release the merge lock if the job holds it; resume `builder-<job-id>` pointing it at `acceptance.md` and `refresh-<n>.md`, and continue at loop step 3.
6. If `ok` is true, the job continues where it was: a job that came from the **Merge queue** rebase or `/factory rebase` stays in its stage and the caller continues (Merging step 2 or nothing), except that a job in the merge queue whose `relock` printed a non-empty `otherJobsFiles` goes to a human first: `relock` has already moved it to `needs-human` with the reason `Refresh <n> changed acceptance tests of other jobs: <files>` and recorded its merge check, so only run `pnpm factory merge-unlock <job-id>` and stop. A job that came from decide's suite failure, the acceptance tester's finding or a rebase conflict continues at loop step 3 (a new review round on the refreshed branch). The job never stops in spec review.

## Merging

Used only by **Merge queue**, never by the loop itself.

1. **Merges run one at a time**: run `pnpm factory merge-lock <job-id>` and wait for it. It returns `acquired: true` once no other job holds the lock; tell the user any `warning`.
2. Run `pnpm factory log <job-id> "Merging: merging the reviewed commit into main"`. Then, in the main checkout, which is already on `main`, run `pnpm factory merge <job-id>`. It merges the commit the reviewers saw (`reviewedCommit`) with `--no-ff` and the message `Merge factory/<job-id>: <title>`, never the branch head.
3. If it returns `status: "conflicts"` (it has already aborted the merge), run `pnpm factory stage <job-id> blocked "Merge conflict with main"` and `pnpm factory merge-unlock <job-id>`, and stop. If it fails because there is no reviewed commit, run `pnpm factory stage <job-id> blocked "No reviewed commit; run the review again"` and `pnpm factory merge-unlock <job-id>`, and stop. If `unmergedCommits` is greater than 0, tell the user that those later commits on the branch were not merged.
4. Otherwise run `pnpm factory test-main <job-id>`. It runs the whole test suite (the `unit` project and every job's acceptance tests) once on the merge commit at the head of `main`; with `FACTORY_TEST_RUNNER=github` it pushes that commit to the temporary branch `factory/merge-check-<job-id>`, runs the suite on that ref on GitHub Actions and deletes the branch afterwards, so `main` is never pushed before its tests are green. Log both projects before you start it, so the cards on the dashboard name the step: `pnpm factory log <job-id> "Merging: running the unit tests on main"` and `pnpm factory log <job-id> "Merging: running every job's acceptance tests on main"`, both before the one `pnpm factory test-main <job-id>` run that covers them. If it prints `ok: false` or fails, reset main to its previous commit with `git reset --hard HEAD~1`, run `pnpm factory stage <job-id> blocked "Tests fail after merge"` and `pnpm factory merge-unlock <job-id>`, and stop.
5. Otherwise run `pnpm factory stage <job-id> merged`, then `pnpm factory push-main <job-id>`, then `pnpm factory worktree <job-id> --remove`, then `pnpm factory check` so every other needs-human job records whether it is still up to date with the new `main` and merges cleanly, and every job in `review` records whether its test merge with the new `main` is clean, has conflicts or fails another job's locked acceptance tests (`message` names them and the fix); report a `tests-fail` job to the user and do nothing else with it.
6. Run `pnpm factory merge-unlock <job-id>`.
7. If `pnpm factory push-main` returned `pushed: false`, tell the user its `warning` (`Merged locally, not pushed: <reason>`). The job stays merged; never push `main` another way and never with `--force`. The user retries with Push main on the dashboard or `pnpm factory push-main <job-id>`.
8. If any other step fails and you stop early, run `pnpm factory merge-unlock <job-id>` before stopping, so the next merge is not blocked.
